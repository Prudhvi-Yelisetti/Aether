## How to run it now

**Packaged (simplest, for actually using it rather than developing it)**:
```bash
~/Aether-x86_64.AppImage
```
Double-clickable too. Starts Ollama (if not running), the backend, and the frontend, opens your browser. Rebuild after any source change with `./packaging/appimage/build.sh` from the repo root — see item 15.

**Dev (for working on the source)**:
```bash
./run.sh
```
Starts Ollama (if not already running), the backend, and the frontend dev server together — see `README.md`'s "Running locally" section. Falls back to port 8010 for the backend if 8000 is already taken by something else on the machine.

Manual equivalent: `cd backend && .venv/bin/uvicorn main:app --reload --port 8000`, then `cd frontend && npm start`. Apply new migrations after pulling: `.venv/bin/alembic upgrade head`. Ollama must be running with `qwen3.5:9b` and `qwen3-coder:latest` pulled — these are the only two models the codebase references (centralized in `routing.py`'s `FAST_MODEL`/`STRONG_MODEL`, see item 9). `qwen3.5:9b` is also the only installed model with vision capability (confirmed live via `GET /api/tags`), which is why it's `routing.py`'s `VISION_MODEL` too.

**Note**: this dev machine reboots or otherwise loses all running processes unpredictably — sometimes mid-session, not just between sessions, and not always with obvious warning (`uptime` has shown as little as 8–14 minutes mid-conversation). Never assume anything is still running without checking first: `ps aux | grep -E "run.sh|uvicorn|react-scripts|ollama|mount_Aether"`, then `curl` each of Ollama (`:11434/api/tags`), the backend (`:8000/` or wherever it's running), and the frontend. `/tmp` gets cleared in the same events — scratch files, logs, and test fixtures written there don't survive; recreate them rather than assuming they're still around. Git commits and the actual source tree are unaffected — only running processes and `/tmp` are at risk.

## Session narrative, in order

### 1. Model-name bug (the real reason the live-LLM path was never tested)

Ollama had been down an entire prior session. Starting it up revealed every LLM call site hardcoded `"llama3"` or `"mistral"` as the model name — neither installed (only `qwen3.5:9b` and `qwen3-coder:latest` are). Every live call failed instantly on "model not found," silently routed to fallback — indistinguishable from Ollama being down at all. Proven live: first test request returned the raw Ollama error string verbatim as the chat response.

**Fixed across 7 files.** Flagged `services/router.py` (a dead, zero-caller duplicate with the same bug) for deletion rather than removing it unilaterally.

*(Resolved 2026-07-23: deleted, after confirming zero references anywhere and no test suite to break.)*

### 2. Latency variance — root cause was `think` mode, not timeout or hardware

Decision-call latency swung 45s–150s+ after the model-name fix. Root cause: `qwen3.5:9b` is a hybrid thinking model and the Ollama payload never set `think`, so every call — including one-line classification prompts — ran an unbounded hidden reasoning trace. A/B proof: 30.9s with `think` unset vs 0.8s with `think=False`, same correct output — **37x speedup**. Fixed via an explicit `think: bool = False` parameter, defaulting off everywhere. Re-verified: 3 consecutive requests, all successful, 5–6s each.

### 3. E2 — first deterministic Validator check

`main.py` computed a failure-string `success` flag for logging but never used it to protect the delivered `response`. Built `services/validation_service.py` as a single source of truth (`FAILURE_PREFIXES`, `validate_response()`) — was duplicated, slightly differently, in `reasoning_service.py`. A real HTTP 500 from a stale import was caught live during the first wiring attempt, fixed, re-verified.

### 4. E3 — bounded retry + escalate, live-proven on all three paths

`validate_response()` classifies each failure as `retryable` or not. New `services/decision_service.py`: one attempt, validate, retry once if retryable, escalate otherwise. Live-verified: normal delivery, immediate escalation for a permanent failure (no wasted retry), retry-then-escalate for a transient failure still failing. **Known gap at the time**: zero backoff between attempts.

### 5. E3 follow-up — retry backoff added, with an honest correction

Added `RETRY_DELAY_SECONDS = 2.0`. First live verification attempt *overclaimed* a result — a real successful recovery, but the log showed no retry had actually fired; it worked for an unrelated reason (lucky timing on a fresh Ollama restart). Caught by checking the log against the claim, corrected with a deterministic test instead: `decide()` called with a fake attempt that fails once then succeeds — confirmed exactly 2 attempts and a measured 2.0s gap matching the delay.

### 6. E2 completed — LLM-based validation, opt-in and observability-only

Added `validate_response_llm()` — asks a model whether a response addresses the prompt. Deliberately **not** wired to gate delivery or retry: off by default (`ChatRequest.llm_validate`), only logs a verdict when enabled. Rationale: an unreliable LLM judge silently rejecting good answers would be worse than not judging at all — needs a monitoring period on real traffic before being trusted to enforce anything. Live-verified three cases: good answer (accepted), off-topic answer (flagged), judge unavailable (fails open, doesn't penalize the response).

### 7. First Tool/Skill expansion — `write_file`, `research_and_save_file`

Closed a real gap: Aether could only read files, never write one. Added `WriteFileTool`/`write_file` (4th Tool) and `ResearchAndSaveFileSkill` (4th Skill), composing the *existing* `WebSearchStep`+`SummarizeStep` with the new `WriteFileStep`. Live-verified the Planner selects it correctly from natural language. **Found, not yet fixed at this point**: `web_search` failed on live attempts with "No useful results found."

### 8. DuckDuckGo + query-extraction fragility, fixed same day

Root-caused item 7's finding: DuckDuckGo's Instant Answer API does narrow exact-topic keying, and `extract_search_query()`'s LLM-extracted phrasing (e.g. "Great Wall of China research") often didn't match it even though the raw topic did — affects the *original* `research_topic` Skill identically. Fixed two things: tightened the extraction prompt to preserve original wording (3 of 4 test prompts now extract cleanly); added a genuine second data source to `web_search.py` — a Wikipedia OpenSearch + summary fallback for when DDG returns nothing. **Caught a real bug in the fallback's own first version**: Wikipedia's API returns 403 without a `User-Agent` header, silently swallowed by a bare `except`. Fixed, re-verified. Full live proof: the exact prompt that failed 100% of the time in item 7 now succeeds on 3 consecutive live attempts, one fully end-to-end (real file, real content).

### 9. Model name centralized, SSH push properly diagnosed

### 13. `llm_validate` run against real traffic for the first time — 18/18 agreement, and two more real bugs found

Prudhvi's call for this session: exercise `llm_validate` on real traffic before considering promoting it from observability-only to actually gating delivery. Created an isolated project (`llm-validate-eval`) and sent 22 varied prompts through `/chat` with `llm_validate: true` — plain factual questions, tool calls, skill calls, and a few deliberately awkward ones (a live-data question the model can't know, a two-part question, an implicit file-content question) — in two batches, comparing the judge's logged verdict against an independent read of each response.

**Result: 18 of 18 applicable judged responses agreed with an independent read** (9 in batch 1, 9 in batch 2; 3 more never reached the judge — 1 caught by the deterministic check first and correctly escalated before the LLM judge ran, 1 crashed before this session's fix, 1 hit an Ollama timeout on a retry-test and never completed). Every pass was a genuinely on-topic, correct answer; every flag was a genuinely bad one — including two separate cases of the exact same underlying bug (`calculate_and_explain`'s explain step going into confused "you've shared a number without context" mode instead of just answering — hit on both "15% of 240" and "√144", confirming it's systematic, not a fluke, though fixing that specific Skill bug wasn't this session's scope). Caveats worth keeping in mind before trusting this fully: small sample (n=18), and the judge model (`qwen3.5:9b` via `generate_strict()`) shares a family with the generator for most of these calls, so correlated blind spots are possible — a judge and generator that fail the same way on the same inputs would still show 100% agreement without actually proving reliability on the cases that matter. **Recommendation: promising enough to justify a bigger batch (50+, ideally including a deliberately-adversarial set crafted to fool the judge specifically), not yet enough to promote to gating.**

**Two real, previously-undiscovered bugs found through this traffic, not through unit tests** (commit `961e2b6`):

- **`research_and_save_file` ignored explicit filenames.** `_build_skill_input()` always derived the output filename via `slugify_filename(query)`, regardless of any filename the user actually typed — "Research the Eiffel Tower and save a summary to eiffel_summary.txt" silently saved as `eiffel_tower.txt` instead. `file_digest` and `find_and_digest_file` both already call `extract_filename(prompt)` first for exactly this reason (see item 10); this branch never did — the same "one fact should have one implementation" lesson item 9 already drew, just in a different spot. The `llm_validate` judge independently flagged this exact response as not addressing the request, which is what prompted the investigation. Fixed: prefer an explicit filename from the prompt, fall back to the slugified query only when the user didn't name one. **Live-verified**: re-ran with a different topic/filename pair ("Research the Great Barrier Reef and save a summary to reef_notes.txt") — response text said `reef_notes.txt`, and `ls ~/aether-workspace/` confirmed the file actually exists on disk under that name, not a slugified topic name.

- **`file_digest` and `research_topic` crashed with a 500 on their success path.** Both Skills end in `SaveMemoryStep`, whose `StepResult.output` is a dict (`{"key": memory_key, "value": value}`) — internal structured data, never meant to be shown to a user, unlike `WriteFileStep`'s human-facing `"Saved to X (Y bytes)."` string. `execute_plan()` returned that raw dict as the chat response regardless, which reached `validate_response()`'s `response.strip()` and crashed with `AttributeError: 'dict' object has no attribute 'strip'` — a full 500, not just a bad answer, for every successful request to either Skill. Root cause of why this went undetected in Phase D/E despite both Skills existing since Phase D: neither had previously been exercised by a broad, uncurated prompt mix through a real `project_id` — every earlier live test of the memory-writing path apparently used `research_and_save_file` (ends in `WriteFileStep`, string output) instead. Fixed with a `_coerce_skill_output()` helper at the Skill→response boundary in `planning_service.py` — the one place that already knows both "this is a Skill's final output" and "this has to become a string for the chat response," rather than pushing the fix into `SaveMemoryStep` itself (which would break the dict shape for any future consumer that wants the structured `key`/`value`) or into `validate_response()` (which has no business knowing about Skill internals). **Live-verified two ways**: the exact crashing prompt through the real `/chat` endpoint (no more 500, clean response); direct invocation of both `file_digest.run()` and `research_topic.run()` against the actual registry, confirming `_coerce_skill_output()` produces `"Saved to memory under 'last_file_digest'."` / `"Saved to memory under 'last_research'."` on each Skill's real success path (`research_topic`'s first attempt hit a genuine Ollama timeout mid-Step and was correctly *not* miscounted as this bug — retried and confirmed the success path separately).

Along the way, also noticed (not investigated further, not a confirmed bug) two batch-2 responses referencing "validation test payload" — a phrase from an unrelated earlier prompt in the same eval project — unprompted, in answers to "boiling point of water" and "president of Brazil." Plausibly project memory picking up eval-batch text and bleeding into unrelated prompts' context, which may just be an artifact of running a mixed eval batch inside one shared project rather than a real bug — flagged for whoever looks at memory-context construction next, not chased down this session.

### 20. Memory architecture rebuilt — semantic vs. episodic, closing a gap flagged since item 13

Prudhvi's ask: make memory more efficient, using human brain structure/function as the design reference. This landed directly on the exact gap Known gaps had been carrying since item 13 — one `Memory` table conflating durable user facts with skill-run artifacts, no relevance filtering, everything dumped into every prompt regardless of topic, mitigated only by a prompt instruction to ignore what isn't relevant (item 14) rather than actually fixed.

Mapped onto Tulving's semantic/episodic memory distinction — a real fit for the actual bug, not decoration: **semantic memory** (durable, context-independent facts — name, stated preferences, from `extract_memory_facts()`) is relevant by construction, the way you don't need a specific cue to recall your own name, so it's still included in full in every prompt. **Episodic memory** (specific past skill-run results — `last_research`, `last_file_digest`, from `SaveMemoryStep`) is only relevant when the current request actually relates to that past event, so it's now retrieved by keyword-overlap cue-matching against the current prompt instead of dumped unconditionally. Also gave episodic memory the brain-like property it never had: bounded-capacity, most-recent-favored retention (`EPISODIC_KEEP=3`) instead of the old behavior of a single row silently overwritten on every new run, which was the wrong kind of forgetting — total loss on overwrite, not graceful decay.

Migration `a91c3d5e7f02` adds a `memory_type` column and drops the old table-wide `(project_id, key)` unique constraint (item f33fab44be66's — incompatible with episodic memory needing multiple rows per key), backfilling existing rows correctly by known key. `storage/project_store.py`'s `save_memory()`/`get_memory()` rewritten type-aware; new `get_relevant_episodic_memory()` does the keyword-overlap retrieval — explicitly scoped and documented as a real but honest heuristic (stopword-filtered word overlap, not true semantic similarity), not oversold as more than it is. `ollama_service.py`/`reasoning_service.py` split the single `memory` param into `semantic_memory`/`episodic_memory` throughout, with framing that matches what's actually true now instead of a blanket hedge. `MemoryPanel.js` shows the real split — "What Aether knows about you" vs. "Recent skill results" — instead of one flat list.

Live-verified end-to-end, not just at the unit level: semantic extraction (real message → correct facts stored/retrieved); episodic write + pruning (ran `FileDigestSkill` 4 times directly, confirmed via SQL that only the 3 most recent survived, oldest evicted); cue-dependent retrieval (an unrelated prompt got zero episodic matches, a related one got all 3); full round-trip through the real `/chat` API (unrelated question stayed clean, related one correctly used the retrieved content); `MemoryPanel.js` verified live via Playwright with a screenshot confirming both sections render correctly with real data.

### 28. `SaveMemoryStep`-vs-Tool question decided: leave as-is, no new Tool

Prudhvi's answer: "whatever is more efficient." Decided against adding a Tool, on two grounds, not just consistency-for-its-own-sake:

- **Code efficiency**: a Tool wrapper would mean a new file, a registry entry, a new `execute_plugin()` dispatch branch, and new `permissions`/`trust_level` metadata to maintain — for something that does nothing `SaveMemoryStep` doesn't already do correctly. Pure overhead, zero functional gain.
- **Architectural efficiency**: a standalone Tool is independently selectable by the *Planner*, outside any Skill. Memory writes today only ever happen through two controlled paths — `extract_memory_facts()`'s LLM-vetted extraction, and a Skill's own `SaveMemoryStep` at the end of a real pipeline. A bare Tool would let the Planner write arbitrary raw text to memory on its own initiative, bypassing both quality controls that exist specifically to keep memory clean. That's a new capability nobody asked for, not a neutral refactor.

No code changed — this is a documented decision closing an open question, not a fix.

## What's already right — keep these


- **Registry-driven decision prompt** (E1) — resist ever hardcoding tool/skill names back into a decision prompt; if a new capability needs special-casing in `planning_service.py`, something's wrong with that capability's `description`, not the Planner. Proven again this session: both new Skills were selectable from natural language the moment they were registered.
- **Model selection vs. capability selection as two separate calls** — matches `ARCHITECTURE.md`'s service boundaries.
- **Graceful multi-layer fallback (LLM → rule → reasoning)** — kept the system usable through Ollama being down, and (double-edged) is exactly what let the model-name bug go unnoticed for as long as it did.
- **Validation and Decision as two separate concerns** — `validate_response()` only classifies; `decide()` only acts on that classification.
- **`experiences.tool_source`** is the one reliable signal for "did the live LLM actually get used" — check it, don't guess from the reply.
- **Compose existing Steps into a new Skill rather than writing new logic** — every new Skill this session reused existing Steps unchanged and added exactly one new piece.
- **A bare `except Exception: return None` can hide a completely broken integration, not just "no results this time."** — the Wikipedia fallback's first version silently ate a 403.
- **Unit tests with clean, short inputs aren't enough for anything that will receive natural language.** `FindFileStep` passed every unit test and still failed live, twice, on realistic sentences.
- **A brand-new UI surface can expose bugs that unit/API tests never would.** The `execute_plugin()` gap (item 12) existed since `write_file`/`list_files` were added, survived every earlier live test, and was only found by clicking through the actual UI with a natural prompt a real user would type. When adding a new interaction surface, re-test old capabilities through it — don't assume passing tests elsewhere means it's covered.
- **A new probabilistic check doesn't have to gate behavior on day one.** `validate_response_llm()` is observability-only until proven reliable — apply the same pattern to future LLM-judged checks.
- **Broad, uncurated real-traffic testing finds bugs that hand-picked live tests don't.** Item 13's crash (`file_digest`/`research_topic`) existed since Phase D and survived every earlier live test because those tests happened to always exercise the memory-writing path via a different Skill. The point of running `llm_validate` on real traffic wasn't just to evaluate the judge — the traffic itself, being varied and somewhat adversarial by design, is what surfaced two bugs the judge didn't even need to catch.
- **Not every Step's output is human-facing text, and that boundary needs one owner.** `WriteFileStep` returns a string meant to be shown to a user; `SaveMemoryStep` returns structured data meant for internal use. `execute_plan()`'s Skill branch is the one place that already knows both "this is a Skill's final output" and "this has to become a chat response" — that's where the dict→string bridge (`_coerce_skill_output()`) belongs, not scattered into individual Steps or into `validate_response()`.
- **A shared Step reused across Skills can't assume every caller's raw text is self-describing.** `SummarizeStep`'s bare "explain this simply" worked by accident for web search results and file content, and failed for bare code output. An optional grounding parameter (`context["question"]`), unused unless a caller sets it, fixed the one caller that needed it without touching the others' behavior at all.
- **Labeling matters as much as content in a local-LLM prompt.** The exact same stored data, labeled "User profile" plus "use when relevant" vs. "Stored context, ignore if not relevant," produced meaningfully different behavior from the same small model on the same underlying rows — worth remembering before assuming a bug needs a schema/architecture fix when a prompt-framing fix might be enough (though see this item's own Known gaps entry for where framing isn't enough).
- **Verify new backend fields end-to-end before building UI on top of them.** Confirmed `llm_validation` persisted correctly via a direct DB read (not just trusting the API response) before wiring the frontend to consume it — the response and the stored row could in principle drift if `add_chat()`'s dict keys ever get out of sync with the response dict's.
- **A "no tables predate this migration" assumption can be wrong even when every existing database confirms it.** Item 15's baseline-migration bug looked, from the one real dev DB available, like a settled historical fact — the bug only existed for a database nobody had ever actually created. Bootstrapping from nothing is worth testing even when there's no obvious reason to doubt the established path.
- **Backgrounding a process inside a bash subshell without `exec` makes `$!` lie about which PID actually matters.** `(cmd) &` captures the subshell's PID, not `cmd`'s, if `cmd` isn't the last thing that subshell execs — `kill "$PID"` then kills a wrapper and orphans the real process. Only found by testing shutdown, not startup — a service that starts fine can still fail to ever actually stop.
- **Check installed capability before choosing a design, not after.** `GET /api/tags`'s `capabilities` field settled both the vision-model question (item 16) and the PDF/DOCX approach (item 17) before any code was written, rather than assuming a model or approach and discovering a mismatch later.
- **A synthetic test built by manually retyping a long string (e.g. base64) across tool calls is a real corruption risk, not just tedious.** Confirmed after the fact in item 16: two copies of the same ~5700-character string differed by 396 characters. Fetch real bytes (`fetch()`, `setInputFiles` on a real file, reading an actual file from disk) instead of hand-embedding long encoded data whenever a test needs exact fidelity.
- **A dev frontend pointed at an already-built AppImage's backend will confidently produce results from stale code.** The squashfs bundle is frozen at build time; a source-level backend fix won't show up in test results run against it no matter how many env vars claim otherwise. Confirm which literal process is answering a request (`ps`, the actual log file) before trusting what a fix "should" have done.
- **A failure that looks identical to a previous one may have a different, unrelated cause.** Item 16's timeout and the earlier "Failed to load image or audio file" both manifested as the same escalation message — investigating the actual backend log each time (not pattern-matching on the user-facing symptom) found two genuinely different root causes.
- **A diagnostic probe that doesn't match production's actual request shape can manufacture an alarming finding out of a real but different bug.** Item 18's first context-window test omitted `think: false` and reproduced the exact unbounded-thinking bug item 2 already fixed — not the context-window bug being investigated. The fix: before reporting a finding as urgent, redo the test with the exact parameters the real code path sends, not a simplified stand-in.
- **Checking how the field actually solves a problem before building a from-scratch solution can save real rework.** Item 21's embeddings upgrade and item 22's consolidation trigger were both checked against real prior art (Letta/MemGPT, Mem0, Zep, Generative Agents) before writing code — confirmed the two-tier memory shape and the sleep/reflection pattern were both established, validated designs, not something to reinvent from first principles.
- **A model's own documentation can catch a mistake a first live test would otherwise blame on the model being weak.** Item 21's first embedding calibration produced poor separation between related and unrelated content — the instinct might have been "this model isn't good enough." Checking `nomic-embed-text`'s model card first found the real cause: a required prefix convention the test had omitted, not a model limitation.
- **A parsing bug in a text-extraction regex can fail silently rather than loudly, and silent failure is worse.** Item 22's CITES-parsing bug didn't crash or error — it degenerated into matching a blank space and produced an empty result, which then correctly triggered downstream rejection. That was lucky, not designed; a differently-shaped bug in the same family (the summary-regex one, same item) did NOT fail safely and wrote corrupted data before being caught. Prefer parsing that fails loudly (raises, or returns a clearly-invalid sentinel) over patterns that can silently degrade to a technically-valid-but-wrong result.
- **An asymmetric-risk decision (fail closed vs. fail open) needs to be made explicitly and justified, not defaulted to whatever the last similar feature did.** Item 22's consolidation verifier fails closed specifically because it writes permanent memory; `llm_validate` fails open specifically because it only skips one observability check. Copying one pattern onto the other without re-examining the actual risk would have been wrong in one direction or the other.
- **A fix for one Step's output shape doesn't mean every sink-ending Skill is covered.** Item 26: fixing `SaveMemoryStep`'s dict-output crash-then-content-loss bug (item 13, then item 26 stage 1) left an identical defect in `WriteFileStep`'s plain-string output completely unnoticed, because it never touched the code path that first fix special-cased. A full audit — checking every Skill against the actual pattern, not just the one that prompted the investigation — found it. When a bug's root cause is "the terminal step's output isn't the real content," check every Skill sharing that shape, not just the one in front of you.
- **A live-verified fix for one Skill is not the same claim as "this class of bug is fixed."** Confirming `research_topic` correctly returns content after item 13's original fix said nothing about `research_and_save_file`, which shared the same underlying flaw (`execute_plan()` only reading the terminal step) through a completely different Tool. Generalizing the fix, then re-verifying every Skill sharing the fixed code path — not just the one that motivated the generalization — is what actually closes a bug class instead of one instance of it.
